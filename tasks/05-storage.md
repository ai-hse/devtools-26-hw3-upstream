# Часть 5. Сохранить данные • 1,5 балла

Контейнер можно заменить в любой момент, а отчёты терять нельзя. В этой части вы подключите постоянное хранилище и напишете `scripts/backup.sh`.

## Опыт: контейнер без хранилища

1. Загрузите два разных CSV и запишите их ID.

2. Перезапустите тот же контейнер и проверьте отчёты.

3. Удалите контейнер, запустите новый и снова проверьте отчёты.

> **На подумать.** Что сохранилось после каждого действия? Сравните число отчётов и их ID.

После опыта остановите и удалите контейнер, чтобы освободить опубликованный порт.

## 5.1. Постоянное хранилище • 0,5 балла

Запустите контейнер готовым скриптом и сравните его с ручным запуском из части 4:

```bash
bash scripts/run-container.sh csv-reports:1 reports-main 18080 reports-data
```

Аргументы по порядку: образ, имя контейнера, порт и том (volume). Скрипт:

- создаёт том и подключает его к `/data`;
- публикует порт на `127.0.0.1`;
- ограничивает контейнер одним CPU и 256 MiB памяти;
- до 30 секунд ждёт готовности сервиса с помощью вашего `probe.sh`;
- при ошибке показывает логи и оставляет контейнер. Занятые имя и порт он не освобождает.

**Проверьте:**

1. Загрузите отчёты, удалите только контейнер и запустите новый с прежним томом. Отчёты должны сохраниться.

2. Запустите второй экземпляр с другим именем, другим портом и новым томом. Его список отчётов должен быть пустым.

3. Посмотрите ограничения CPU и памяти основного контейнера через `docker inspect`.

## Опыт: кто может писать в том?

Приложение в контейнере работает от пользователя `10001:10001`. Проверим, что произойдёт, если этому пользователю не разрешить запись.

1. Создайте отдельный том. Через вспомогательный Linux-контейнер положите в него файл и сделайте каталог тома доступным только пользователю `root`. Файл нужен, чтобы Docker не перенёс в пустой том исходные права из образа API.

2. Запустите API с этим томом в `/data`, отдельным именем и свободным портом. Посмотрите состояние контейнера и его логи.

3. Исправьте владельца или права каталога через вспомогательный контейнер. Не разрешайте запись всем пользователям.

4. Запустите новый API-контейнер с другим именем и тем же томом. Проверьте `/health` и загрузите CSV.

> **На подумать.** Почему один процесс не смог записать данные, а другой смог? Что изменилось после исправления прав?

Удалите контейнеры и том этого опыта. Том `reports-data` с отчётами не удаляйте.

## 5.2. Резервная копия и восстановление • 1 балл

Том переживает пересоздание контейнера, но и сам может потеряться. Напишите `scripts/backup.sh`.

Аргументы по порядку: каталог данных и путь к архиву.

**Требования:**

- Скрипт архивирует содержимое каталога данных в `tar.gz`, включая скрытые файлы. Исходные данные он не меняет.
- Пути в архиве отсчитываются от корня каталога данных, чтобы при распаковке не появлялся лишний уровень `work/backup-data`.
- Если архив с таким именем уже есть, скрипт завершается с ненулевым кодом и не трогает его.
- Код `0` скрипт возвращает только после того, как полный архив создан.
- При ошибке чтения или записи скрипт возвращает ненулевой код, пишет причину в stderr и удаляет неполный архив, который успел создать.
- Неверное число аргументов, отсутствующий каталог данных и ошибки доступа тоже приводят к ненулевому коду.

В проверках путь к архиву всегда лежит вне каталога данных, а его родительский каталог существует. Символических ссылок в путях нет, поэтому проверять вложенность и обрабатывать ссылки не нужно.

### Подготовить данные

Для резервной копии нужен **отдельный контейнер с bind mount**: каталог `work/backup-data` с вашей машины монтируется в `/data` контейнера.

1. Создайте `work/backup-data` и запустите контейнер с отдельным именем на свободном порту.

2. Проверьте, что приложение может записывать данные, а ваш пользователь может их читать. Если контейнер не запустился, найдите причину в логах и исправьте доступ.

3. Загрузите в этот экземпляр два отчёта.

4. Остановите контейнер, чтобы данные не менялись во время копирования.

На macOS Docker передаёт файлы хоста в свою Linux-среду. Права bind mount могут отличаться от прав в именованном томе. Запись для всех пользователей не разрешайте.

### Восстановить

Отдельный `restore.sh` не нужен: восстанавливайте вручную.

1. Создайте архив:

   ```bash
   mkdir -p work/backups
   bash scripts/backup.sh work/backup-data work/backups/reports.tar.gz
   ```

2. Распакуйте его средствами `tar` в **новый пустой каталог**. Пользователь приложения должен иметь доступ к распакованным данным. Сохранять исходных владельцев файлов не нужно.

3. Запустите сервис с этим каталогом и проверьте ID и содержимое отчётов через HTTP.

> **На подумать.** Чем отличаются том, bind mount и архив? Какую задачу решает каждый из них: пережить обновление контейнера, видеть файлы с хоста или восстановиться после потери рабочего каталога?

Архив и рабочие данные не коммитьте, но сохраните их. Перед частью 6 остановите одиночные контейнеры.
