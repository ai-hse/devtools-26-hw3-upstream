# Часть 4. Упаковать сервис в Docker • 2 балла

На вашей машине всё работает, но у коллег может не быть нужного Python-окружения. В этой части вы создадите `Dockerfile` и `.dockerignore`, упакуете сервис в образ и выясните, что видит контейнер.

Образ собирается из корня проекта:

```bash
docker build -t csv-reports:1 .
```

## 4.1. Образ и HTTP • 1 балл

**Требования:**

- В образе есть Python 3.12, он запускается командой `python3`.
- В образ входят зависимости из `requirements.txt`, код и HTML-шаблоны приложения.
- Параметры `HOST`, `PORT` и `DATA_DIR` образ принимает через окружение. По умолчанию сервер слушает порт `8080` на сетевом интерфейсе контейнера и хранит данные в `/data`.
- Диагностические сообщения приложения идут в stdout и stderr, чтобы их было видно через `docker logs`.

## 4.2. Пользователь, контекст сборки и кэш • 1 балл

**Требования:**

- Процесс работает от непривилегированного пользователя с UID и GID `10001:10001`.
- Данные хранятся в `/data`. Каталог создаётся в образе, его владелец `10001:10001`. Приложение может писать в пустой том Docker, смонтированный в `/data`.
- Инструкцию `VOLUME` в Dockerfile не используйте. Сначала вы изучите хранение внутри контейнера, а в части 5 подключите хранилище явно при запуске.
- В контекст сборки не попадают `.git`, `.venv`, `.env`, рабочие данные, логи и резервные копии. Реальные секреты для проверки этого требования не добавляйте.
- Если кэш доступен, правка только Python-кода не заставляет заново устанавливать зависимости.

## 4.3. Опыт: сеть

1. Убедитесь, что порт хоста `18080` свободен.

2. Запустите контейнер без публикации порта. Проверьте `/health` **изнутри контейнера** любым способом, доступным в образе.

3. Обратитесь к контейнеру с Linux-хоста по `127.0.0.1:18080` и запишите результат.

4. Пересоздайте контейнер с публикацией порта хоста `18080` в порт контейнера `8080`. Повторите запрос с хоста и загрузите CSV своим `submit.sh`.

5. Остановите и удалите этот контейнер, чтобы освободить порт. Создайте новый с той же публикацией, но задайте серверу `HOST=127.0.0.1`. Сравните доступ изнутри и снаружи.

6. Пересоздайте контейнер с рабочими настройками. Он понадобится в следующем опыте.

> **На подумать.** Чем результат шага 3 отличается от запроса изнутри контейнера? Где находится `localhost` в каждом из запросов? Почему одного `EXPOSE` недостаточно, чтобы достучаться до сервиса через порт хоста?

## 4.4. Опыт: что контейнер видит отдельно от хоста

Возьмите работающий контейнер без подключённого хранилища.

1. Найдите на Linux-хосте PID главного процесса контейнера. Внутри контейнера прочитайте `/proc/1/cmdline`. Сопоставьте команды и номера процессов.

2. Запустите второй контейнер из того же образа без публикации порта. Сравните hostname двух контейнеров.

3. Создайте файл `/tmp/only-first` в первом контейнере и проверьте, что во втором его нет.

4. Сравните `uname -r` на хосте и в обоих контейнерах.

> **На подумать.** Почему оба сервера могут слушать внутренний порт `8080`? Есть ли у каждого контейнера своё ядро? Свяжите наблюдения с пространствами имён (namespaces) PID, UTS, mount и network. Чем такое устройство отличается от отдельной ВМ?

После опыта удалите второй контейнер.

## 4.5. Опыт: кэш сборки

1. Добавьте комментарий в Python-код и пересоберите образ. По выводу сборки убедитесь, что шаг установки зависимостей взят из кэша.

2. В той же рабочей копии добавьте комментарий в `requirements.txt` и снова пересоберите образ. Сравните вывод с предыдущей сборкой. Время в секундах измерять не нужно.

3. Уберите оба комментария. Остальные изменения решения сохраните.

> **На подумать.** Какие шаги выполнились заново во второй сборке и почему?

Для части 5 оставьте один исправный контейнер без хранилища.
