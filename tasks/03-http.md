# Часть 3. Сделать надёжный HTTP-клиент • 1,5 балла

Сервер может ответить ошибкой, редиректом или оборвать передачу на середине. Клиент должен сохранить только полный успешный отчёт, а в остальных случаях сообщить об ошибке. В этой части вы допишете `scripts/submit.sh` и `scripts/probe.sh`.

## 3.1. Что можно узнать из HTTP-ответа?

Запустите сервер. Загрузите `samples/clean.csv` запросом `POST /reports` в формате `multipart/form-data`. Имя поля с файлом – `file`.

1. Сохраните тело и заголовки ответа на загрузку в разные файлы. По адресу из заголовка `Location` получите созданный отчёт.
2. Найдите тот же запрос в логе сервера по `X-Request-ID`.

> **По желанию.** Сравните ответы на три запроса: `GET` по несуществующему пути, `DELETE /reports` и `POST /reports` с JSON вместо файла. Что в каждом случае нужно исправить в запросе?

Маршруты и коды ответов собраны в [справке по API](../interfaces.md#http).

## 3.2. `submit.sh`: загрузка и обычные ошибки • 0,5 балла

Запустите текущий `submit.sh` с корректным CSV. Затем отправьте повреждённый CSV, указав тот же выходной файл. Для обоих запусков сравните код завершения и содержимое файла. Возьмите файл, который не жалко перезаписать.

> **На подумать.** Скрипт сохранил JSON-ответ. Значит ли это, что он сохранил отчёт?

Исправьте `scripts/submit.sh`:

```bash
bash scripts/submit.sh http://127.0.0.1:8080 samples/clean.csv work/from-api.json
```

Аргументы по порядку: базовый URL, путь к CSV и путь к выходному JSON.

**Требования:**

- При HTTP 201 скрипт сохраняет тело ответа в выходной файл и возвращает `0`.
- При другом HTTP-статусе, сетевой ошибке или отсутствии входного файла скрипт возвращает ненулевой код и пишет причину в stderr.
- Если запрос неуспешен, выходной файл не создаётся и не перезаписывается.
- Если не удалось записать результат, скрипт возвращает ненулевой код, а старый выходной файл остаётся целым.
- HTTP 3xx считается ошибкой. По редиректу скрипт не переходит.
- Один запрос длится не больше 10 секунд. Повторять POST автоматически нельзя.

В проверках базовый URL имеет вид `http://127.0.0.1:PORT`, без пути и без `/` в конце. Каталог выходного файла уже существует, входной и выходной файлы различаются.

**Проверьте:** создайте выходной файл с любым содержимым, отправьте повреждённый CSV и убедитесь, что содержимое файла не изменилось.

## 3.3. `probe.sh`: отвечает ли сервис • 0,5 балла

Допишите `scripts/probe.sh`:

```bash
bash scripts/probe.sh http://127.0.0.1:8080/health
```

**Требования:**

- Скрипт выполняет GET по **полному URL** из аргумента.
- Код `0` скрипт возвращает только при HTTP 200 и успешно завершённой передаче.
- HTTP-ошибка, редирект, отказ соединения и таймаут дают ненулевой код.
- Скрипт ждёт ответа не дольше трёх секунд. Повторов и перехода по редиректам нет.

В отдельном терминале запустите имитацию сервера:

```bash
.venv/bin/python tools/http-fixture.py --host 127.0.0.1 --port 8090
```

У неё есть такие GET-маршруты:

| Маршрут | Ответ |
|---|---|
| `/ok` | 200 |
| `/unavailable` | 503 |
| `/slow` | Ответ через 15 секунд |
| `/redirect` | 302 с `Location: /ok` |

1. Проверьте все четыре маршрута своим `probe.sh`.

2. Получите сам ответ `/redirect`, а затем конечный ответ после перехода по редиректу. Сравните их.

3. Запросите `/unavailable` обычным `curl` и посмотрите на HTTP-статус и `$?`. Повторите со своим `probe.sh`.

4. Остановите имитацию и повторите запрос. Сравните отказ соединения с ответом 503.

## 3.4. `submit.sh`: обрыв передачи и сигналы • 0,5 балла

**Требования:**

- Статуса 201 недостаточно: передача тела ответа должна завершиться успешно. Обрезанный ответ считается ошибкой. Не оставляйте его копию рядом с выходным файлом.
- Временные файлы удаляются при успехе, при ошибке и при прерывании через `SIGINT` или `SIGTERM`.

### Почему отчёт обрезан, хотя статус 201?

У имитации сервера есть `POST /reports`. Он принимает загрузку и отвечает 201, но обещает в `Content-Length` больше байтов, чем передаёт на самом деле, и обрывает соединение.

Снова запустите имитацию и передайте её базовый URL своему `submit.sh`. Проверьте код завершения, что прежний выходной файл цел и что временных файлов не осталось.

> **На подумать.** По каким признакам ответа можно заметить такой сбой?

### Что останется на диске после прерывания загрузки?

1. Перезапустите имитацию на том же адресе и порту с параметром `--upload-mode slow`. В этом режиме POST ждёт 15 секунд перед ответом.

2. Запустите `submit.sh` и нажмите `Ctrl+C`, пока он ждёт ответа. Когда скрипт завершится, проверьте, что старый выходной файл цел, а временные файлы удалены.

3. Снова запустите загрузку и отправьте процессу `submit.sh` сигнал `SIGTERM` из второго терминала. Временные файлы проверяйте после того, как скрипт завершится.

Мгновенно завершаться скрипт не обязан: Bash обработает сигнал, только когда завершится дочерний процесс.

Перед частью 4 остановите сервер и имитацию.
